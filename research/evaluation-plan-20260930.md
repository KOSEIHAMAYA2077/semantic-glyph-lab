# 次の試作の比較・評価計画

2026-09-30 / **未実施の計画**。[方針](roadmap-20260930.md)の判断を、同じ人工入力と同じ画面条件で確かめるための設計。以下の目標値はプロジェクト内の暫定基準であり、先行論文が保証する性能ではない。

応用試作へ進む際は、[一般PCへの軽量化方針](consumer-pc-20260930.md)に従い、研究品質と実行時の負荷を比較する。現在の研究条件は以下のまま維持する。

## 1. 基準と評価の分離

基準版は `prototype-v0.5.0`（`d9b6a3f60906adf81f63f3f211190950999e3613`）。基準のコード・モデル・結果を置き換えず、別出力へ記録する。過去の[6生成](../experiments/end-to-end/RESULTS.md)や[流体実験](../experiments/fluid-surface/README.md)は少数条件の観察で、一般的な成功率ではない。

段階を切り分ける。

1. 意味: 日本語から取り出した対象・属性・関係が合っているか。
2. 形: 同じ英語説明を与えたとき、生成メッシュが指定を満たすか。
3. 表面: 同じメッシュと文字に、各描画方式を適用したときどう違うか。
4. 統合: 書き続ける・待つ・取り消す・形が替わる場面で本文と動きが保たれるか。

前段が失敗した例を除外して全経路の成功率を高く見せない。生成失敗、ロード失敗、タイムアウト、意味の不一致を別に数え、全試行数を分母に残す。

## 2. 表面の比較

最初に既知の600秒の失敗を、旧条件の44書記素・atlas 8×8・密度15・128²格子・力0.4・明示4点補間のまま再現する。その後、下表の新しい比較条件へ移る。密度や文字数を変えた結果を、旧条件の完全な再現とは扱わない。

F0（現方式）、F1（短い移流写像の交替）、F2（文字IDを持つ面配置）を、同じ静止球と手続き花瓶で比較する。良さそうな方式を選んだ後、立方体、メビウス、既存の人工生成じょうろへ広げる。母体の変形は最初OFF、後から同じ変形量でONにする。全形状・全密度・全seedを最初から総当たりしない。

| 固定するもの | 比較条件 |
|---|---|
| 入力 | 人工の日本語・英字・記号、結合文字、空白・改行を含む文字列。原文と描画用書記素を別に記録 |
| 密度 | 初めは512書記素相当で統一。採用候補だけ64・2048・4096相当も調べる。入力数と描画での反復数を併記 |
| 画面 | 1280×900、DPR1、同じカメラ・照明・黒背景・文字サイズ。近景と全景の両方を残す |
| 流れ | 同じ速度場、刻み、seed、渦の強さ。固定比較ではseed 20260930。追加2seedで偶然よい例だけでないか確認 |
| 記録時点 | 0・60・300・600・1800秒。まず36,000固定ステップで既知の600秒の失敗を再現する。固定刻みの検証と、候補の30分の実時間での連続動作を別記録にする。実時間・積分時刻・総ステップ・停止や背景化を併記 |
| 更新の瞬間 | F1/F2の更新前・中・後を短い動画で保存。停止画だけでちらつきや巻戻りを合格にしない |

古い文字を白、新しい入力だけを指定色にした条件も設ける。ここで調べるのは追加入力ごとの色の独立性であり、全体の色をそろえた見栄えではない。

### 記録する指標

| 観点 | 記録方法と暫定の採用条件 |
|---|---|
| 原文保全 | 受理した入力ID、正規化前の全文、色指定を期待列と照合。欠損・再試行による二重受理0を必須とする。描画上の反復は別に数える |
| 字形 | 同じ面上の追跡点と近景を使い、300/600/1800秒で線へ退化する領域、二重字、急な消失を比較。透視短縮や裏面による不可視を字形崩壊と混ぜない |
| 被覆 | 物体マスクを画面上の区画へ分け、前面の各区画の文字画素率と基準との差を記録。細部・裏面は別方向から確認。画素率だけで3D表面積の被覆を保証しない |
| 歪み | 座標写像がある方式はJacobian、写像微分の最大伸長・縦横比の分位値、非正のセル数を記録。面積が保たれても細長く伸びるので符号だけで判定しない。F2はパッチの伸縮・反転・面からの距離を測る。異なる表現の数値を同一指標の順位にしない |
| 連続性 | 更新時刻を記録して動画と照合。局所的な交替が点滅・巻戻りとして見えないか、担当者と確認方法を明記して判定する |
| 負荷 | モデル停止・画面を前景にした状態でフレーム間隔median/p95を測定。まず60fps相当を目標、30fps未満が続く条件は既定にしない。rAF間隔をGPU時間とは呼ばない |
| 長時間 | 0・10・30分でメモリと資源数を採取。入力がないのに増え続ける場合は不採用。JS/WebGLエラーも保存 |

文字の読める割合や自然さをエージェントが目視した場合は、その事実を明記する。ユーザーテストや人間参加者による評価とは呼ばない。文字が読めること、流れが自然であること、形が判別できることを一つのスコアへまとめない。

採用条件は、**既存方式より長時間の字形・被覆が改善し、更新のちらつきや大きな性能低下を持ち込まないこと**。折返し0やエラー0だけで完成扱いにしない。30分の成功から一日中の安定性も推定しない。

原文と文字IDが保存されることと、同じ表示文字の軌跡が連続することは別要件とする。特にF1では模様を交替させるため、1文字の移動を保証するとはしない。追跡可能な表示インスタンスは位置・向き・表示状態を記録し、追跡できない方式は「軌跡は未保証」と明記する。面の模様として採用する場合にもこの制限を残す。

## 3. 形状生成の比較

Cubeの利用条件と1例の実行が確認できた場合に限り進める。取得revision・設定・ハッシュ・依存・利用条件の出所を記録し、モデルごとに環境を分ける。原本メッシュは残し、共通の寸法・向きに正規化した表示用データを別に作る。

最初に以下を**開発用の公開例**として使う。すでに相談・調整に使った語なので、未見性能の証拠にはしない。

| 群 | 人工入力の例 | 見る項目 |
|---|---|---|
| 基本形 | 球体／立方体／細長い直方体 | 明示した形、軸比、不要な突起 |
| 物体 | 剣／花瓶／じょうろ | 物体を識別できる部位と接続、裏側の形 |
| 属性と数 | 取っ手が二つ付いた丸い花瓶 | 二つの部位があるか、左右や接続が一致するか |
| 複合 | 花瓶から木が生えている | 二つの対象、接触、上下関係 |
| 曖昧・非形状 | 今日は少し迷っている | 無理に物体へ変えない制御。形生成の画質評価とは分ける |

日本語→短い英語の前処理を一度保存し、同じ英語をShap-E・Cube・画像経由へ渡す比較を先に行う。画像経由では同じ画像生成設定・中間画像・前景マスクを保存する。画像→メッシュ部分だけを比較する際は入力画像自体を固定する。

動作確認1例の後、まず代表3例でメモリと所要時間を調べる。継続可能なら、固定した6条件×各3seedへ進む。同じseed番号でもモデル間で同じ乱数結果にはならない。調整後には物体名・言い回し・関係の組合せを分けた別の人工12例を固定し、設定変更前にコミットする。結果を見て調整したらその12例は以降、回帰用と扱う。学習へ進む場合は、評価側と同じ言い換えやテンプレートが学習側へ入らないよう分割する。

各例に、対象一致、属性一致、個数、接続、裏面、細い部位、読込成功、面数を別々に記録する。形の判定は前・横・後と回転動画を使い、最もよい1枚だけを載せない。採用判断は平均の美しさだけでなく、同じ入力の失敗例も含める。

待ち時間は「初期ロード」「前処理」「形生成」「読込」「入力から表示まで」を分ける。メモリ不足とタイムアウトも失敗に数える。最初の安全な1例の計測後、比較本番の前に上限時間を固定する。32GBの統合メモリを32GBの専用VRAMと同一視しない。他サービスの利用状況を記録し、既存サービスを無断で停止・再設定しない。

品質がよくても待ち時間が執筆と合わなければ「事前生成した候補」への採用に留める。少数の勝ち例から、任意の文章に対する優位を主張しない。公開条件が未解決なら生成物やスクリーンショットも公開せず、判断の記録だけを残す。

## 4. 部分編集と統合

初期の編集比較は、部位が既知の手続き花瓶で行う。「口だけ広く」「胴だけ四角く」「取っ手だけ大きく」の3操作を用いる。名詞の認識・部位対応・変形を分け、編集部位の寸法変化と、維持部位の頂点位置・大きさの変化を記録する。対応のない生成メッシュ同士には同じ頂点誤差を使わず、形状距離と見た目を別に比較する。指定部位が存在しない・対応を決められない場合は明示的に失敗とし、元の形と原文を保持する。

統合前後で、生成中の連続追記、後追いの属性、取消、古い応答、失敗後の再試行、IME変換、色の独立、文字数上限を確認する。[現在の連続入力の検証](../experiments/writing-preview/README.md)を参照し、原文保持と表示上の反復を混同しない。

球→花瓶のように頂点数も穴の数も違う形は、単純な頂点補間で変形できるとは仮定しない。最初は原文・色・入力IDを引き継いだ表示の切替として検証する。連続した形態変化や文字ごとの位置の対応付けは、その後の独立課題とする。

## 5. 実験記録の単位

後続実装では新しい `experiments/<実験名>/<未使用のrun名>/` を作り、次を一組として残す。今の文書追加ではこの実験出力はまだ作らない。

- `manifest.json`: コードcommit、方式、モデルrevision、取得元と条件、seed、人工入力ID、端末、設定、実行時刻。
- `results.json`: 全試行の成功・失敗・時間・負荷。未測定を0として記録しない。
- `ASSESSMENT.md`: 問い、比較、担当者と確認方法、採用範囲、失敗、未解決点。
- 比較画像・短い動画・許可された生成物: 同じ視点・時刻・条件を対応付ける。配布条件が未解決なら公開Gitへ含めない。

UIや自動テストの成功は、意味の正しさや好ましい見た目の代わりにはならない。次の版の採用は、数値・画面・失敗記録を合わせて判断する。
