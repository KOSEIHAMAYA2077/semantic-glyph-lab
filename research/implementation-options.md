# 文章に関連した立体へ、蓄積した文字を這わせる実装方針

2026-09-30の実験に基づく方針。Apple M5・32GBのMacで行った人工例の実験を根拠とする。既存アプリを変更せず、この別リポジトリで比較している。同じ日本語3例から2経路で作る計6生成を完了し、三方向の形と文字の表示を比較した。

## 推奨する構成

**意味検索と手続き形状で即座に反応し、そこでは表せない対象だけを、8Bモデルによる短い説明と非同期の立体生成へ渡す構成を推奨する。表示は一つの共通描画部へ集め、既定は文字が面全体を覆う方式とする。**

この構成なら、文章を加えた直後の変化と、未知の物体が現れる変化を両立できる。今の実測では意味検索は数ms、部品合成と説明は数秒、立体生成は数十秒という違いがある。毎回の入力をすべて3D生成へ渡すと、書く速度と画面の反応が合わない。逆に、24種のカタログだけでは新しい名詞や複合物を表せない。

未知形の生成経路は、この段階では一つに固定しない。直接Shap-Eと画像経由を同じ描画部へ渡し、部品の接続、薄い面、裏側など、対象に必要な特徴ごとに比較する。工程が少ないことだけで直接生成を優先したり、一度きれいにできた物体から画像経由が常に優れると結論したりしない。推奨しているのは上記の一つの段階式構成であり、生成モデルの優勝を決めることではない。

現時点では各方式を選んで実行する試作が動く。以下の自動振り分け、一定周期の意味更新、日常の執筆との連動は**次の実装案**であり、この新しい試作で完成した機能としては扱わない。

## 三つの処理を分離する

```text
入力文 ──→ 対象・特徴・関係の解釈 ──→ 形の取得 ──→ 共通の三角メッシュ
   │                                    │                   │
   │                    手続き形状 / 部品合成 / 既存素材 / 生成 │
   └──→ 原文の文字・追加時刻・指定色 ───────────────────────────→ 表面表示
```

1. **意味の解釈**は「何を、どういう姿で、どこへ」を決める。物体名、四角さや細長さ、数、部品の関係、対象不明を分ける。文章全文の英訳と、立体に必要な短い説明の抽出は別の仕事である。
2. **形の取得**は、その解釈から頂点と三角面を得る。検索は既存形を選び、部品合成は配置し、生成モデルは新しい形を出す。これらを同じ能力として数えない。
3. **表面表示**は、取得方法によらず同じ文字の履歴を使う。モデルへ渡した英語で原文を置き換えない。文字の流れ、物体全体の回転、母体のゆっくりした変形も独立に制御する。

共通化により、「名詞の解釈は正しいが、生成した穴が塞がった」「形は読めるが、文字が首の部分から消えた」を別々に直せる。元のGLBを残し、表示用の正規化や変形はその派生データに適用する。

## 文字を「面として」見せる判断

**現段階の既定は三方向からの文字テクスチャ投影とする。** UVがない生成メッシュにも同じ処理を使え、少ない入力を反復して面全体を読ませられる。入力の実数と表示上の文字数は区別する。一度書いた文字が一度だけ現れる方式ではない。斜めの面で投影が混ざり、文字の可読性が落ちる点は残る。

比較用の「面を歩く」は、各文字の中心を三角面上の座標で保持し、隣接面へ連続的に移す。文字の一つ一つが動くことは分かりやすい。一方で、平面の文字板の角は急な曲面から浮いたり、面の内側へ隠れたりする。中心を正しく載せるだけでは、文字全体が皮膚のように曲がるわけではない。

移流の初版では、文字が花瓶の中央へ集まって首が黒くなった。速度を流れ関数から求める修正版では、同じ2,000点を60秒動かした高さ8区間の分布変動量が、生成花瓶で0.3590から0.0165へ減った。高さだけの指標で、移動距離も完全には揃えていないため、面全体の均一性の証明とはしない。[比較と画像](../experiments/advection/RESULTS.md)

母体の揺らぎは文字の流れと分離して実装済み。低ポリゴンでも文字中心を変形後の三角形から再構成し、面に沈む退行を修正した。馬のモデルで4,096文字・移流・変形を同時に動かした240フレームは、このMacでrAF間隔p95 16.70msだった。長時間や他端末、同時に重い生成を動かした負荷の保証ではない。[実画面と測定](../experiments/surface-03/low-poly-motion/RESULTS.md)

両方式とも、圧力や粘性を解く物理流体シミュレーションではない。次の描画改善は、文字の板を小さな曲面パッチへ曲げる方式と、UVを作って面内で文字を動かす方式の比較が候補になる。これは未実装の提案であり、3D生成モデルを替えて解決する問題ではない。

## 次の実装順序

1. **文と表示を独立に進める。** 追記した原文と色を保持し、入力の区切りで解釈を要求する。生成待ち中も既存の形と文字を動かす。遅い応答が後の選択を上書きしない要求IDは既に導入している。毎キーの生成、無制限の待ち行列は作らない。
2. **既知形・属性・未知対象を振り分ける。** 明示語や十分な根拠のある意味検索は既存形へ、属性だけなら今の母体を変形する。組み合わせが核なら部品合成へ、カタログにない対象なら8B説明と生成へ進める。「どの形か不明」と「モデル/APIが使えない」を別に返す。この統合された自動振り分けは未実装。
3. **生成結果を候補として扱う。** 英語説明と形を別々に確認できるようにし、現在の母体を保ったまま採用・保留を選べるようにする。形の大きさ・向きの正規化、有限値・面数・読込検査は実装済みだが、意味の一致の判定はしていない。人物や作品を含む未知語も必ず忠実に作れるとはしない。
4. **周期変化は意味と母体の変形を分ける。** 文章が変わらない間は、流れや母体の揺らぎを連続的に変える。別の意味の形へ移す場合は、一定間隔で直近の文章から候補を更新する。まず手動の区切りで意図が伝わることを確かめ、その後周期化する。長文から取り出した一部分と全文理解を混同しない。

利用者向けには、黒い空間、入力、必要な短い説明を中心にする。比較用のモデル名や測定値は研究画面へ置き、普段の画面に常時並べる必要はない。今の試作は入力をメモリ内に保持するだけで、日記保存や他のアプリの入力との連動はこの構成にはまだ接続していない。

## 将来、何を学習すればよいか

**今回、モデルの追加学習はしていない。** 使ったのは公開済みモデルの推論、プロンプト、手続き形状、描画アルゴリズムである。最初の学習対象には、大きな3D生成モデルを一から作るよりも、文章から小さな構造化された形の説明を得る部分を推奨する。

- 教師データは、公開可能な人工の日本語、対応する物体・属性・数・部品関係、手続き形状のパラメータ、参照用の三方向画像を一組にする。形データの出所・ライセンス・生成seedを残す。「対象がない」「複数の候補がある」「以前の形への編集」も含める。
- 名詞だけでなく、色と形の区別、どの部品を修飾するか、否定、左右、貫通、接触を教師にする。LLMが作った説明は人が形と照合するまで正解にしない。使用中の個人原稿を自動で教師データへ取り込まない。
- まず文章→構造のモデルを学習し、構造→配置は検査可能な規則で実装する。その次に、文章と形・複数方向画像の対応を学習する検索を試す。形の生成を学習する場合は、検索の成否と新規生成の成否を分ける。
- 未見評価は、同じ形の言い換えが学習側と評価側へ漏れないよう形・文章の系列単位で分ける。さらに「既知名詞と新しい属性の組み合わせ」「未見の部品関係」「カタログ外の名詞」を別枠で先に固定する。最後の枠は、未知と正しく返す能力と、本当に新しい形を生成する能力を区別する。
- JSON成立、対象の一致、部品と接続の一致、三方向からの読み取り、文字の面被覆・連続性、待ち時間を別々に記録する。繰り返し修正に使った例は回帰試験に移し、新しい評価例で確認する。形だけ正しくても文字が載らないものは、この用途での完成とはしない。

この方向に関連する一次研究は、言葉と形の対応を扱う [Text2Shape](https://arxiv.org/abs/1803.08495) と、言語・画像・点群の共通表現を扱う [OpenShape](https://arxiv.org/abs/2305.10764)。どちらも今回のMacで学習・再現した研究ではない。手続きツールを言語モデルが操作する [3D-GPT](https://arxiv.org/abs/2310.12945) も設計上の参考になるが、現試作は任意コードを生成・実行せず、上限のある部品JSONに限定する。論文の位置付け、未実行の理由、関連する文字表現の研究は [調査記録](language-to-shape.md) に分けてある。

## 実行と公開の範囲

現時点では端末内推論を用い、通常APIは入力文・生成画像・GLBをファイルへ保存しない。研究として保存するのは明示した人工例だけ。公開重みは出所・revision・hash・読込形式を確認し、専用環境で扱う。モデルに任意のPython/JavaScriptを出力して実行させる経路はない。ブラウザ外の入力監視も追加していない。

作業中に確認した `.local` 全体は約42GB、空きは約1.4TiB。これは環境・比較に使ったモデル・失敗記録などを含む途中の占有量で、単独モデルの容量や総ダウンロード通信量ではない。形の語彙を増やすために、取得可能な素材を無目的に全量収集する必要はない。

利用条件は一律ではない。MiniLM・Qwenは公式のApache-2.0、TripoSRはMIT、Kenneyの採用素材はCC0。Shap-EはMITだが、公式モデルカードの商用利用に関する非推奨記述も区別して残す。SDXL Turboは固定revisionのStability AI Community Licenseに従う研究・非商用評価として扱っており、生成物をこのリポジトリのコードと同じ条件に読み替えない。画像経由については **Powered by Stability AI**。[MiniLM公式](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2)、[Qwen8B公式](https://huggingface.co/Qwen/Qwen3-8B-MLX-4bit)、[TripoSR公式](https://github.com/VAST-AI-Research/TripoSR)、[Kenney公式](https://kenney.nl/assets/nature-kit)、[Shap-E公式モデルカード](https://github.com/openai/shap-e/blob/main/model-card.md)、[取得したSDXL Turboのライセンス](https://huggingface.co/stabilityai/sdxl-turbo/blob/71153311d3dbb46851df1931d3ca6e939de83304/LICENSE.md)

TripoSGはトップレベルのMIT表記と個別ソースの条件が重なるため、公開する経路には採用していない。原本と不採用の試行は保全し、公開可否を未確認のまま成功例に含めない。[確認した範囲](../experiments/advanced-mesh/README.md)

## 追加の同一入力比較を踏まえた判断

「小さな帆船」「開いた傘」「長い注ぎ口が付いたじょうろ」を一度ずつ英語化し、同じ説明を各方式へ渡した。3件とも物体と主な条件を保持し、6個のメッシュを得た。[全結果と6枚の比較画像](../experiments/end-to-end/RESULTS.md)

じょうろは画像経由で胴・取っ手・長い注ぎ口を明瞭に保ち、直接生成では部品の切れと浮遊片が多かった。帆船はどちらも読めるが、画像経由の方が太いマストと部位の接続を保った。傘では直接生成の薄い面が自然で、画像経由は柄が残る代わりに裏側が厚い塊になった。今回の崩れは、名詞の英訳よりもメッシュ生成後の部品・厚さに現れた。

生成待ちは直接生成が約41〜48秒、画像経由が約16〜18秒。ただし常駐・読み込み・キャッシュの条件が違い、各1回の実使用待ち時間である。段階式の推奨構成は維持し、未知形の生成方式を一律に固定しない。画像経由をまず試せる実用候補として残し、薄い面などは直接生成と比較する。採用判定では三方向の見え方と文字の載り方を見る。自動で方式を振り分ける機能は未実装である。

今後の比較を増やす場合も、3例×1seedからの一般化を避け、最初に対象・条件・判定基準を固定する。HTTP200や閉曲面だけを成功と数えず、浮いた部品、塞がる穴、文字が見えない細い部分も残す。
