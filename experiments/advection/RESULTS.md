# 三角面上の文字移流 — 比較記録

2026-09-30。独立入口は `/src/advection/preview.html`。メイン描画は変更していない。

## v1 / v2: 文字中心を三角面上に保持

人工例文の2,000文字を三角形の面積に比例して配置。文字ごとに三角形番号と重心座標を持ち、辺を越すと隣の三角形へ進む。移動方向と文字の向きは法線間の回転で運ぶ。再配置・瞬間移動は行わない。三角形の接続は位置を1e-6単位で照合し、UVの継ぎ目をつなぐ。面が黒い深度遮蔽物となり、背面の文字を隠す。

v1は1ステップ24面までの制限に球の極付近で1回到達した。安全上限を96へ広げたv2では、4形状・各2,000文字・30秒の固定刻みで上限到達も開境界での停止も0。v1のソースと全測定を保存している。

### 実時間の測定 (v1)

M5 / Chrome / ANGLE Metal、1280×900、DPR 1。読み込み完了後12秒の実RAF観測。単位ms。CPU時間は更新と描画命令送信までで、GPU処理時間そのものではない。

| 形 | 三角形数 | 構築 | CPU中央値 / p95 | RAF間隔中央値 / p95 |
|---|---:|---:|---:|---:|
| 球 | 6,768 | 26.0 | 0.8 / 0.9 | 16.7 / 16.7 |
| 数式花瓶 | 25,632 | 99.1 | 0.9 / 1.1 | 16.7 / 16.8 |
| Shap-E花瓶外殻 | 112,520 | 553.6 | 1.4 / 1.7 | 16.7 / 16.7 |
| 立方体 | 9,408 | 27.7 | 1.9 / 3.4 | 16.7 / 16.7 |

生成花瓶の初回観測は578フレーム・積分時間9.65秒だった。ほかは723フレーム・約12.05秒。フレーム刻みは35msで制限し、最初の10フレームを分位値から除いているため、中央値だけで初回の停止を含む平均60fpsとはいえない。CPU時間には読み込み、最初のGPU準備、距離検査を含めない。初回の待ちを隠した性能保証はしない。

### 貼り付きと文字板 (v2)

各物体の最大寸法を2.6に正規化。30秒の固定刻みを進め、同じ配置でサイズのみ変更した。2000文字中65中心・260隅を抽出して最近接三角面との距離を調べた。中心の最大距離は全例2.30e-16以下。ただし描画中心は深度競合を避けるため法線方向に0.002だけ外へ出す。

| 形 | 文字板の一辺0.04: 隅の最大距離 | 0.09 | 0.17 |
|---|---:|---:|---:|
| 球 | 0.0043 | 0.0080 | 0.0140 |
| 数式花瓶 | 0.0101 | 0.0305 | 0.0631 |
| Shap-E花瓶 | 0.0277 | 0.0624 | 0.1188 |
| 立方体 | 0.0197 | 0.0447 | 0.0847 |

距離は符号なしで、外への浮きと内側への食い込みを区別しない。板の中心が貼り付いても板全体は曲面に沿わない。立方体の角では中心が隣面に移る瞬間に文字板が90度回転する。花瓶の急な曲率では文字の一部が黒い本体に隠れ、細い首や縁で欠ける。サイズを小さくするとこの誤差は減るが、文字は読みづらくなる。

### 可読性と密度

球の正面では一文字ずつ読め、輪郭では自然に薄くなる。三平面投影の重複はない。一方、別々の文字同士の重なりはあり、文字列の読む順序は維持しない。上向き方向は曲面に沿って回転する。大きい文字ほど面の輪郭を越えて飛び出す。

初期配置が面積一様でも、正規化した接ベクトル場は密度を保持しない。生成花瓶を高さ8区間へ分けると、上端2区間の文字は初期284→30秒31へ減った。60秒では中央へ強く偏った（`run-v2/density.json`）。首が黒くなる原因にはこの偏りと板の隠れの両方がある。これは流体シミュレーションではない。

### 判定

隣接面を跨ぐ連続移動の基盤として採用。メインの面テクスチャをこのまま置き換えることは見送る。現方式は「表面にある小さな札」であり、面全体を覆う文字テクスチャとは別の見た目になる。次は流れ関数で密度偏りを減らす比較。板の浮きは別に、面に沿う小さなパッチやUV面内移流を比較する必要がある。

## v3: 流れ関数による密度偏りの軽減

入口は `/src/advection/preview.html?flow=stream`。元の正規化場はパラメータなしで引き続き比較できる。

頂点へスカラーψを与え、各三角面内で線形補間する。`v = n × grad_surface ψ`を使い、速度の長さは正規化しない。共有辺のψが同じなので、辺を通る流量が隣面と一致する。辺に達した後は残り時間を隣面の速度で進める。ψは高さと三つの滑らかな空間パターンの和で、パターンの係数だけ時間変化させる。圧力や粘性を解く物理流体シミュレーションではない。

同じ初期2,000点、60秒、1/60秒刻み。高さ8区間の文字数を初期サンプルと比べた総変動量 `sum(abs(after-before)) / (2*2000)` は以下になった。0なら区間ごとの文字数が初期と同じ。高さだけの粗い指標であり、面全体の均一性や見た目の良さを証明するものではない。

| 形 | 元の正規化場: 60秒の変動量 | 流れ関数: 60秒の変動量 | 流れ関数: 平均移動距離 |
|---|---:|---:|---:|
| 球 | 0.1005 | 0.0180 | 8.64 |
| 数式花瓶 | 0.2115 | 0.0230 | 9.15 |
| Shap-E花瓶 | 0.3590 | 0.0165 | 9.43 |
| 立方体 | 0.0700 | 0.0160 | 7.84 |

元の場は一定速度0.18なので60秒の距離は約10.8。新方式は場所により速度が変わり、平均距離もやや短い。同じ移動距離へ厳密に揃えた比較ではない。初期と60秒の生成花瓶の高さ別文字数は、旧 `[291,314,416,372,222,101,112,172] → [78,98,514,671,543,41,30,25]`、新は同じ初期から `[282,295,428,374,235,105,110,171]`。文字の移動は十分にあり、単に停止させて分布を固定したわけではない。

`run-v3/normalized-generated-60.png`と`stream-generated-60.png`を見比べると、新方式は細い首と口に文字が残り、形が読みやすくなった。全8条件で境界停止・96面上限到達0。辺の流量一致と連続積分のテストを追加した。板の浮き、文字同士の重なり、欠けは解決していない。

### v3 実時間確認

同じ環境で12秒ずつ再測定。4形状とも722–723フレーム、積分時間12.02–12.07秒。CPU中央値 / p95は球2.4 / 2.8ms、数式花瓶0.8 / 3.6ms、生成花瓶3.4 / 4.2ms、立方体2.5 / 3.1ms。RAF間隔は中央値16.7ms、p95は16.7–16.8ms。実行時のJITや並行負荷が異なるため、v1との数msの差を厳密な速度比較には使わない。`run-v3-realtime/measurements.json`へ保存。

### 任意入力へつなぐアダプタ

`src/advection/layer.ts`の`AdvectionLayer`を追加。`constructor(geometry, field, count=2000)`、`group`、`update(dt,time,glyphSize)`、`dispose()`。共通LetterFieldのテクスチャ・グリッド・リビジョンを参照するため、追加した文字と色をそのまま板に使える。粒子数を入力数より多くした場合は書記素を繰り返す。入力が粒子数を越えた場合は末尾の粒子数分を表示し、古い文字はLetterFieldには残るが全て同時には表示しない。

借用した物体geometryとLetterField/textureを破棄しない。形が変わったら呼出側でレイヤを作り直す。静的メッシュに対する任意選択肢であり、この担当ではメイン描画を変更していない。型検査と7テスト通過。

実ブラウザでは追加文字数とgridだけの確認では不十分だった。`adapter-check/`と`adapter-check-v2/`は91書記素・grid16の値は正しくても、画像には元の@を四分割した白い模様しか出なかった。原因は共通LetterFieldで同じCanvasTextureの寸法を512→1024へ変更しても、既存のGPU領域が再確保されないこと。`adapter-check-before-atlas-fix/`でGLエラー1281・黄色ピクセル0を記録した。

呼出側がテクスチャの寸法変更時にGPU領域を解放する修正を行い、`adapter-check-after-atlas-fix/`の通常経路でGLエラー0・黄色23,372ピクセルを確認した。日本語・数字が黄色で表示され、古い@は白いままになることを画像確認した。テスト側でだけ同じ対処を実施した中間検証も`adapter-dispose-probe/`へ残している。レイヤ自体は借用textureの解放を行わない。
