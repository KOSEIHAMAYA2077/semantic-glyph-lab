# 連続入力へ接続する前の設計

2026-09-30 15:42 JST。v0.3.0を保存した後の案。まだ画面・APIへ接続していない。

## 目的

文章は送信直後から現在の面に加わる。意味の判断や新しい立体の生成を待たずに次の文章を書ける。原文と指定色は描画側が保持し、意味モデルの返す英語に置き換えない。

## 比較の前提

input-routingの24人工例を、事前固定した規約・同じ8Bモデル・一度ずつで評価する。新規物体、現在形への編集、形を維持する文を分ける。未知名詞をカタログの近似形へ押し込む失敗を重く見る。結果を見て接続範囲を決める。

## 最小構成の候補

- 新しい試験モードとして追加し、既存6方式を残す。最初は手動送信を区切りとし、自動周期・他アプリの監視は含めない。
- 原文の受理と形の処理を分ける。受理した文章は一度だけ追加し、生成失敗でも消さない。未受理の入力は入力欄に残す。
- 後続の「四角く」が生成途中の対象へかかるよう、処理時点で直前の確定形を文脈にする。単純に最後の入力だけへ上書きすると対象名を失うので、その方式は避ける。
- 待ち行列は上限を設ける。上限を超えた文章を無言で捨てたり、書いた文字を二重追加したりしない。APIが失敗した場合も同じ文の自動再送を繰り返さない。
- 手動の形選択やモード切替は待機処理より優先する。形の世代番号と読み込み番号で古い応答を無効にする。ブラウザの中止とバックエンド推論停止は同義ではないので、資源が解放されたと主張しない。
- 生成済みの未知形は、その対象の短い説明と属性を保持する。属性編集で球体などへ差し替えず、保持してある元メッシュから変形する。
- 形を持たない日記文や色だけの指定は文字だけ加え、形は維持する。失敗理由や待機は短い操作表示に留める。

## 確認項目

生成を待つ間の追記、未知形の後の属性編集、API失敗での原文保持、手動選択後の遅い応答、待機上限、色の履歴、複数回送信での二重追加防止、既存モードの回帰を確認する。モデル精度と画面の非同期制御の試験は別にする。


## 初回ルータの結果を受けた変更

v1は形式成立3/24、厳格な操作契約0/24で、未知名詞の不当近似や否定の意味誤りがあった。実際に球体1個を表せる例もあるため、0/24を視覚上の成功率とは扱わない。画面へは接続しない。

CPU側は独立に `src/intent.ts` と `src/continuous.ts` を準備する。待機入力を勝手に文章へまとめずFIFOで解釈し、生成処理も同じworker内で順番に動かす。生成中に追記が来たら、生成済みの結果をすぐ表示せず、待機文を先に解釈する。対象が同じなら最新属性で採用、対象が変わっていれば前の生成結果を破棄する。待機は8入力まで、超過は受理せず下書きへ残す案。対象の世代と、原文の通し番号は分ける。これは現在のUIとは未接続。

意味側は、操作と物体の説明・属性を分ける二段階案と、同じ条件の14Bモデル比較へ進む。結果が改善しても、再利用24例と新規12例の成績を混ぜない。
