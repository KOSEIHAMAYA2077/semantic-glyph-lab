# 同じ24例・同じ指示で8Bと14Bを比べた結果

2026-09-30 15:54〜15:56 JSTに14Bを各例1回実行。形式は大きく改善したが、**そのまま連続入力へ接続する案は不採用**とする。未知名詞を現在の物体の編集へ寄せる誤り、否定の誤読、英語への誤変換が残る。

これは同じ24人工例を再利用した一つの条件での比較。新しい未見評価ではなく、日本語一般の成功率でもない。元の採点条件とraw出力は変えていない。

| 厳格なschema成立 | 3/24 | 23/24 |
| 事前に固定した機械的操作契約 | 0/24 | 16/24 |

14Bの機械的契約16/24には、「急須」を `kamaboko` にする1件が入っている。評価を後から書き換えず、**契約通過に加えて未知語の意味確認も通るものは15/24**と別に示す。これも全入力の意味を完全に評価する指標ではない。逆に「球体をひとつ」は正しいsphereを返したが、明示した `count:1` を省いたため、元の厳格規約では両モデルとも不一致。既定値なら球1個になることは残しておく。

## ほかに残る失敗と改善

- `四角くしないで。` は、両モデルとも四角さを0へ戻す編集となった。変更の禁止と既存属性の解除を混同する。
- `立方体ではなく球に変えて。` は、14Bでも `changes:{form:"sphere"}` となる。newへ切り替えず、許可しない属性キーで拒否される。14Bの唯一のschema違反。
- `四角くねじれた花瓶。` は、現在のsphereに四角さ・ねじれを加えた。修飾語を取り出せても、新しい名詞への変更を落とす。
- `円環を8個。` は `new / object_en:"8 rings"` で、意味のある説明は返したが、既知ringとcountを使う操作契約には合わない。これを単純に言語の誤りとは数えない。
- 生成済みじょうろの四角化、軽い縦長化、色だけ・抽象文・引用文での形保持、既存対象の属性編集・個数編集・粗さ解除は、14Bでは規約どおり受理できた。

8Bに多かった `edit / keep` の余分なtargetは14Bで消えた。したがって、この条件では規模を増やす価値はあった。ただし形式の改善だけでは、自動的な形の置換を任せられるとは判断しない。未知物体を正しく扱うには、現在の形へ引き寄せない対象抽出と、new/editの判定を引き続き分けて調べる必要がある。これは次の設計仮説であり、今回追加検証していない。

## 測定・取得・再現の範囲

公式Qwen3-14B-MLX-4bit、revision `ba63a5141812f9870287df53341123a71ba41433`、Apache-2.0、group128/4bit safetensors。必要10ファイル7,862,396,465 bytesを新しいローカルフォルダへ取得し、全SHA256・サイズを照合した。重み2本は公式LFS SHA256とも一致。1,007 tensorのヘッダとindexも一致した。取得元と個別hashは [model-manifest.json](model-manifest.json)。追加の依存導入・量子化・モデルコード取得はない。

元の24例、prompt、schemaはバイト一致。8Bと14Bのtokenizer、語彙、chat templateもバイト一致を確認した。同じ既存専用MLX環境、greedy温度0、thinkingなし、最大384 tokens、seed17、例ごとの再試行なし。元runnerとの差分は、モデルファイル照合・場所・記録先・推論なしの検証入口・比較注記のみ。ロード後の生成と採点の処理は変えていない。

14Bのload呼び出しは1.801秒、プロセス最大RSSは約2.496GB。重みhash検査直後であり、MLXの遅延処理もあるため、これは完全な冷起動時間ではない。MLX peakとRSSは異なる指標で、加算しない。単独の生成プロセスの記録であり、Mac全体の利用量や他モデルと同時実行できる上限を表すものでもない。GPU推論は他担当と時間を分けた。Pythonで拒否したIP接続試行は0。
